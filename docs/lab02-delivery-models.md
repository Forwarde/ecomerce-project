# ЛЗ 2. Выбор модели поставки и развертывание рабочего пространства

## 1. Сравнение и выбор модели поставки для трех кейсов

| Критерий оценки | Кейс А: Внедрение СЭД в госоргане по тендеру | Кейс Б: Новый мобильный продукт стартапа с непроверенной гипотезой | Кейс В: Миграция монолита банка в облако |
| :--- | :--- | :--- | :--- |
| **1. Неопределенность требований** | **Низкая:** жесткое ТЗ по госзакупкам, СТ РК и регламентам документооборота | **Высокая:** продуктовая гипотеза не подтверждена рынком, частые пивоты | **Средняя:** бизнес-логика известна, но высока техническая неопределенность миграции |
| **2. Стоимость ошибки** | **Высокая (юридическая/финансовая):** штрафы по госконтракту, срыв сроков приемки | **Низкая на итерации, высокая при долгой разработке не того продукта** | **Критическая:** простой банковских операций, нарушение требований регулятора (НБ РК / АРРФР) |
| **3. Регуляторика и комплаенс** | **Жесткая:** Закон РК «О госзакупках», ЭЦП (НУЦ РК), ИБ-аттестация ГТС | **Минимальная на старте:** базовое соблюдение Закона РК о ПДн | **Максимальная:** требования банковского надзора, PCI DSS, локализация данных |
| **4. Зрелость и доступность заказчика** | Заказчик общается официальными письмами и принимает работу по актам | Основатели и пользователи доступны ежедневно для быстрой обратной связи | Внутренний заказчик (ИТ-дирекция и ИБ) вовлечен, но требует четких архитектурных гейтов |
| **5. Распределенность и структура команды** | Подрядчик + рабочая группа госоргана с формальным согласованием | Кросс-функциональная продуктовая команда (4–7 чел.) | Несколько команд (Platform, Core Banking, Security, SRE) с жесткими зависимостями |
| **6. Тип контракта** | **Fixed Price** с поэтапной закрывающей документацией | Внутреннее финансирование (Seed/Pre-seed) или **Time & Materials** | **Гибридный / Capped T&M** с фиксированными вехами (Milestones) |
| **Рекомендуемая модель поставки** | **Predictive (Waterfall / V-Model)** с фазовыми гейтами и формальным контролем изменений | **Adaptive (Scrum + Dual-Track Discovery/Delivery)** с короткими спринтами 1–2 недели | **Hybrid (Фазовое планирование вех + итеративная поставка по паттерну Strangler Fig / Kanban)** |

## 2. Выбор модели поставки для сквозного проекта AtelierFlow (ADR-001)

Для проекта **AtelierFlow** выбрана **гибридная модель (Scrumban / Iterative Delivery с фиксированными учебными вехами)**.
Полная архитектурно-управленческая запись оформлена по стандарту MADR в файле:
- [`docs/adr/ADR-001-delivery-model.md`](./adr/ADR-001-delivery-model.md)

### Краткая выжимка ADR-001 (по шаблону MADR):
* **Контекст:** Команда из 4 студентов разрабатывает ИС для швейного ателье за фиксированный срок 15 недель с жесткими контрольными точками (рубежные контроли на 8-й и 15-й неделях), но уточняемыми требованиями заказчика.
* **Рассмотренные варианты:**
  1. *Чистый Waterfall* — отвергнут (высокий риск сдать в конце семестра неудобный интерфейс для закройщиков).
  2. *Чистый Scrum с 2-недельными спринтами* — отвергнут (высокие накладные расходы на ритуалы при плавающем учебном расписании студентов).
  3. *Гибрид (Scrumban + 3 фиксированных релизных инкремента)* — **принят**.
* **Последствия:**
  - *Положительные:* Непрерывный поток задач с WIP-лимитами, еженедельная синхронизация и гарантированная сдача артефактов к вехам курса.
  - *Отрицательные / Риски:* Требует дисциплины ведения доски GitHub Projects и строгого соблюдения WIP-лимитов.
