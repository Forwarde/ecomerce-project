| Уровень тестирования | Объем автоматизации | Инструмент (Open Source) | Что проверяется в AtelierFlow | Где запускается |
| :--- | :---: | :--- | :--- | :--- |
| **1. Статический анализ и проверка типов** | 100% | **ESLint + TypeScript (`npm run lint`, `npm run build`)** | Типизация моделей заказа, клиента, мерок, отсутствие синтаксических дефектов | Автоматически в `.github/workflows/ci.yml` |
| **2. Безопасность цепочки поставок (SAST / SCA)** | 100% | **Aqua Security Trivy** | Уязвимости `CRITICAL/HIGH` в зависимостях `ITProjects/package-lock.json` | Автоматически в `.github/workflows/ci.yml` |
| **3. Нагрузочное тестирование НФТ (Load / SLA)** | 100% | **Grafana k6 (`k6/load-test.js`)** | Выполнение NFR-01 и NFR-02: `p(95) < 1000 мс` и ошибки `< 5%` при 10 одновременных VUs на `/` и `/login` | Автоматически в `.github/workflows/k6.yml` |
| **4. Проверка API и маршрутов** | 80% | **Hoppscotch / Bruno + cURL** | Проверка кодов ответа `200 OK` для публичных страниц и `307 Temporary Redirect` для защищенного `/admin` | В CI и локально перед релизом |
| **5. Приемочное тестирование (UAT)** | Ручное по чек-листу (100% покрытие MVP) | **Браузер (Edge / Chrome) + стенд `localhost:3000`** | Сквозные бизнес-сценарии закройщика и администратора ателье (8 сценариев ниже) | Перед сдачей релиза с участием заказчика |
| **6. Мониторинг доступности в эксплуатации** | 100% (24/7) | **Uptime Kuma (Docker)** | HTTP-пинг `http://localhost:3000` каждые 60 сек для контроля SLA 99.5% | Контейнер мониторинга |

## 3. Безвинный Postmortem инцидента (Blameless Postmortem)

### Паспорт инцидента: `INC-2026-01` — Невыполнение автоматических проверок CI после добавления воркфлоу
* **Дата инцидента:** Ноябрь 2026 г. (коммиты до `2c617ce`).
* **Длительность (Time to Detect + Time to Mitigate):** 45 минут.
* **Влияние на проект (Impact):** Пайплайн `AtelierFlow CI Pipeline` не запускался автоматически при пушах в `main`, из-за чего 2 коммита прошли без автоматической проверки линтером и сканером `Trivy`. Пользовательский функционал сломан не был.

### Хронология событий (Timeline)
* **14:10** — Разработчик создал файл пайплайна `ci.yml` внутри вложенной папки приложения `ITProjects/.github/workflows/ci.yml` и запушил в `main`.
* **14:15** — Команда заметила, что во вкладке **GitHub Actions** репозитория не появилось ни одного запуска (`0 workflow runs`).
* **14:30** — Диагностика показала, что GitHub Actions считывает YAML-файлы воркфлоу строго из корневой директории репозитория (`/.github/workflows/`), а не из подпапок монорепозитория.
* **14:55** — Выпущен фикс-коммит [`2c617ce`](https://github.com/Forwarde/ecomerce-project/commit/2c617ce) (`fix: переместил папку .github в корень репозитория`) с настройкой `defaults.run.working-directory: ./ITProjects`. Пайплайн `AtelierFlow CI Pipeline #1` успешно запустился и прошел за `1m 46s`.

### Вклад системных факторов (Root Causes — без поиска виноватых)
1. **Структура репозитория:** Код Next.js-приложения лежит во вложенной папке `./ITProjects`, поэтому при работе из IDE папка `.github` была по привычке создана рядом с `package.json`.
2. **Отсутствие проверки статуса CI в чек-листе DoD на старте:** До этого случая в команде не было правила обязательно открывать вкладку `Actions` сразу после пуша инфраструктурных изменений.

### Что сработало хорошо
* Быстрая диагностика и чистый фикс через `defaults.run.working-directory: ./ITProjects` без необходимости перекраивать структуру всего репозитория.

## 4. Эксплуатационный Runbook: Перезапуск сервиса AtelierFlow и проверка здоровья после сбоя

### Назначение
Пошаговая инструкция для дежурного инженера или администратора при срабатывании алерта недоступности `AtelierFlow` (`HTTP != 200` на порту `3000`). **Целевой RTO ≤ 15 минут.**

### Шаг 1. Диагностика состояния (2 минуты)
1. Проверить статус контейнеров и потребление памяти:
   ```bash
   docker compose ps
   docker stats --no-stream
   ```
2. Вывести последние 100 строк логов веб-сервера для определения причины сбоя:
   ```bash
   docker compose logs --tail=100 atelierflow-web
   ```

### Шаг 2. Восстановление сервиса (5 минут)
1. Перезапустить контейнер приложения в штатном режиме:
   ```bash
   docker compose restart atelierflow-web
   ```
2. Если проблема вызвана последним обновлением кода — откатиться на предыдущий стабильный коммит и пересобрать контейнер:
   ```bash
   git revert HEAD --no-edit
   docker compose up -d --build
   ```

### Шаг 3. Верификация после восстановления (Smoke Check — 3 минуты)
1. Проверить код ответа главной страницы и страницы авторизации:
   ```bash
   curl -I http://localhost:3000
   curl -I http://localhost:3000/login
   ```
   *(Ожидаемый ответ: `HTTP/1.1 200 OK`)*.
2. Проверить, что защита `/admin` активна:
   ```bash
   curl -I http://localhost:3000/admin
   ```
   *(Ожидаемый ответ: `HTTP/1.1 307 Temporary Redirect` на `/login`)*.
3. Убедиться, что монитор в панели **Uptime Kuma** (`http://localhost:3001`) перешел в статус **UP (Green)**.
