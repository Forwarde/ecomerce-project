# ADR-001: Выбор модели поставки для системы «AtelierFlow»

* **Статус:** Принято (Accepted)
* **Дата:** 18.09.2026
* **Авторы:** Нурлы (PM/DevOps), Нурым (Backend Developer)

---

## 1. Контекст (Context)
Разрабатывается система учета заказов, мерок клиентов и склада тканей «AtelierFlow» для реального швейного ателье (заказчик — Айбол). Проект реализуется командой из двух человек в условиях жестких учебных дедлайнов и регулярного уточнения требований от заказчика. Необходимо выбрать оптимальную модель и архитектуру поставки сервиса.

---

## 2. Драйверы решения (Decision Drivers)
* Ограниченные ресурсы команды (2 разработчика).
* Заказчик не имеет технического бэкграунда и инфраструктуры (нужно максимально простое развертывание).
* Высокая скорость разработки первого протокола (MVP).
* Минимальные затраты на сопровождение и инфраструктуру (бюджет близок к нулю).

---

## 3. Рассмотренные варианты (Considered Options)
1. **Вариант 1 (Выбран):** Монолитный REST API на FastAPI в связке с PostgreSQL, разворачиваемый через Docker Compose на недорогом VPS.
2. **Вариант 2 (Отвергнут):** Микросервисная архитектура (отдельный сервис склада, сервис заказов, сервис клиентов, API Gateway) в кластере Kubernetes.
3. **Вариант 3 (Отвергнут):** Бессерверная архитектура (Serverless / FaaS на базе облачных функций AWS Lambda / Yandex Cloud Functions).

---

## 4. Сравнение вариантов и почему отвергнуты альтернативы

### Вариант 2: Микросервисы + Kubernetes
* **Плюсы:** Независимое масштабирование модулей, изоляция сбоев.
* **Минусы:** Избыточная сложность оркестрации, огромные накладные расходы времени команды на настройку сети, мониторинга и CI/CD вместо написания бизнес-логики. Неоправданно для нагрузки одного ателье.

### Вариант 3: Serverless (Бессерверная архитектура)
* **Плюсы:** Оплата только за фактические вызовы, нет необходимости администрировать ОС сервера.
* **Минусы:** Проблема «холодного старта» (cold start), привязка к конкретному облачному вендору (Vendor Lock-in), сложности локальной отладки и миграции базы данных.

---

## 5. Принятое решение (Decision)
Выбрать **Вариант 1**: Монолитное модульное приложение на FastAPI + реляционная БД PostgreSQL с поставкой через Docker Compose.

---

## 6. Последствия (Consequences)

### Позитивные:
* Быстрый запуск первой рабочей версии (MVP) силами двух человек.
* Простота локального тестирования и единый репозиторий.
* Низкая стоимость хостинга (достаточно одного минимального VPS).

### Что мы теряем / Негативные последствия:
* **Сложность горизонтального масштабирования:** при резком росте нагрузки придется масштабировать всё приложение целиком, а не отдельные нагруженные узлы.
* **Связанность кода:** требуется строгая внутренняя дисциплина в кодовой базе, чтобы модули склада и заказов не превратились в запутанный клубок зависимостей.
